## Ordered steps

1. Create the .NET solution and React TypeScript client skeleton using the versions recorded in
   `docs/conventions.md`; keep module boundaries explicit.
2. Define room working-hours and availability interfaces, including timezone-aware boundaries and
   deterministic free-slot enumeration.
3. Implement reservation value objects and validation for future starts, 15-minute alignment,
   duration limits, working hours, and UTC normalization.
4. Implement transactional reservation creation with a database-level overlap safeguard so
   concurrent requests cannot both succeed.
5. Implement conflict details and the bounded 30-day, same-duration alternative search with
   proximity ordering and earlier-before-later tie-breaking.
6. Add server-side authentication and member authorization; ensure owner and role values are
   derived from the authenticated principal rather than request data.
7. Expose the booking flow through the API with field-level validation errors and privacy-safe
   conflict responses.
8. Build the client booking form and success/conflict/error states, preserving the displayed
   timezone and allowing a suggested slot to be selected and retried.
9. Add unit, integration, concurrency, API, and component tests mapped below; update the
   verification contract and run `scripts/check`.

## Risks & open questions

- **No application code exists yet.** Recommendation: establish the smallest runnable solution and
  test harness first, because the verification contract is currently a greenfield no-op.
- **Working-hours data and timezone source are not yet modeled.** Recommendation: define a room
  timezone plus weekly working periods in the Rooms module, with UTC conversion at the boundary;
  this matches BR-3 and BR-8 without leaking storage types across modules.
- **PostgreSQL overlap enforcement may require a database-specific constraint.** Recommendation:
  use a transaction plus an exclusion constraint (or the closest equivalent supported by the chosen
  schema approach), and prove it with a concurrent integration test rather than relying only on
  application checks.
- **The exact authentication provider is not implemented.** Recommendation: use ASP.NET Core
  Identity as required by `docs/security.md`, with test principals for member and unauthenticated
  cases; do not add an external identity dependency.
- **The client framework test runner is unspecified.** Recommendation: select the lightest
  maintained runner compatible with the chosen React setup, record the dependency decision for
  human approval, and keep component tests focused on observable states.
- **Alternative proximity ties can produce multiple valid candidates.** Recommendation: centralize
  ordering as absolute start-distance, earlier start, then later start, and test exact ordering so
  the response is deterministic.
