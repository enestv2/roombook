## Ordered steps

1. Confirm the existing API routes, DTOs, error payloads, and authentication schemes so the document
   describes the actual contract rather than inventing a parallel API.
2. Add the selected maintained OpenAPI/Swagger package with an explicit version and record the
   dependency rationale; do not add an external hosted documentation service.
3. Register a versioned OpenAPI document with API title/version, operation metadata, bearer security,
   UTC/offset timestamp formats, validation constraints, conflict examples, and sanitized
   ProblemDetails schemas.
4. Enable `/swagger/v1/swagger.json` and `/swagger` only when `IHostEnvironment.IsDevelopment()` is
   true; keep authentication, CORS, and controller behavior unchanged.
5. Add integration tests using the existing ASP.NET test host to verify the Development document,
   UI, security metadata, representative schemas/examples, and non-Development absence.
6. Run `scripts/check`, perform an independent read-only review, and map each acceptance criterion
   to test or reproducible route evidence.

## Risks & open questions

- **New dependency approval is required.** Recommendation: use Swashbuckle.AspNetCore at a current
  .NET 10-compatible stable version because it is widely used, integrates with ASP.NET Core
  controllers, and can generate both JSON and Swagger UI without changing runtime endpoints.
- **The API currently has no explicit XML documentation pipeline.** Recommendation: prefer explicit
  OpenAPI operation/schema metadata first; enable XML comments only if the generated document lacks
  required descriptions and then suppress only the narrowly justified compiler warning.
- **Development-only routing must be tested with separate environments.** Recommendation: use the
  existing WebApplicationFactory configuration to boot Development and Production hosts, proving the
  route gate rather than relying on manual inspection.
- **Error schemas may be inferred inconsistently from custom ProblemDetails responses.**
  Recommendation: register a stable ProblemDetails schema and explicit response metadata so clients
  can rely on the documented error shape without exposing implementation details.
